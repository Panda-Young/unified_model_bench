## --no-baseline 开关（单 backend 干净测量）
- 背景：--backend X 会强制 auto-add CPU baseline（为对比），导致单 backend 测量仍被 CPU 污染；
  且实测顺序跑时后段 activation 会被前面残留抬高基数而低估（NCNN_CPU_BF16 activation=5.6MB 假象）。
- 实现：cmd_args 加 --no-baseline（BenchConfig.no_baseline）；benchmark_runner auto-add CPU 逻辑加
  !cfg_.no_baseline 条件；无 baseline 时 accel 置哨兵 kNoBaselineAccel=-2.0（result_collector.hpp 常量），
  CSV 三分支（失败< -1.5 全 "-" / no-baseline==-2 保留 timing+内存、diff/accel 打 "-" / 正常），
  Run 汇总循环同步处理。已验证三分支行列数一致（26 逗号/27 字段）。
- 用法：unified_bench.exe model.onnx --backend ncnn_cpu_bf16 --no-baseline
- 测量语义实证：进程工作集不含 GPU 显存（VRAM）；顺序跑时后端自身峰值高于前面则不污染（DML 110 vs CPU 66），
  若低于前面则 activation 低估（NCNN BF16 案例）。

## --per-process 跨进程 diff 对比（--dump-output / --baseline-file / --baseline-ms）
- 需求：--per-process 下每个 backend 独立进程（无同进程 baseline），diff 对比不能丢。
- 方案：调度器先跑 CPU baseline 子进程（追加 --dump-output <path>），子进程把首个输出写文件
  （uint64 count + float 数组）+ "<path>.avg" sidecar 记录 avg_ms；调度器读 sidecar 得 baseline_ms；
  其余子进程追加 --baseline-file <path>（加载对比算 max_diff/avg_diff）与 --baseline-ms <ms>（算 accel）。
- TestBackend 对比优先级：跨进程 baseline 文件 > 同进程 baseline > -2 哨兵；dump 输出在 free(odata) 前。
- baseline 文件路径：<output_dir|.>/<base>_<backend>.out（extract_base_name + backend 名）。
- 验证：cl /Zs 通过；Python 验证 dump/load roundtrip（float32 无损）与对比公式一致。
- 行为：baseline 行本身 diff/accel 为 "-"（它是基准）；其余 backend 行有真实 max_diff/avg_diff/accel。

## 修复：NCNN Vulkan extract(out0) 硬崩溃 0xC0000005（NCNN_VK/_BF16/_FP16 全挂）
- 症状：test_model.onnx（in0=1,3,224,224 / in1=1,48,1,1 / out0=1,10，双 4D 输入）三个 Vulkan
  后端 warmup extract out0 全部 HW exception 0xC0000005；CPU 后端正常。
- 根因（python ncnn 走中间 blob 定位）：崩溃层 = **BinaryOp add_0（cat 输出 3D 224×224×48 + in1 4D Mat）**。
  ncnn **Vulkan BinaryOp shader 只支持 dims<=3 广播**，4D 输入参与广播越界 → 段错误；
  CPU 广播逻辑健壮所以正常。次要问题：旧 MakeMatFromShape 用外部 flat buffer 直包装 Mat，
  外部 stride 与 ncnn cstep（16 字节对齐）不一致时会错位。
- 修复（src/ncnn_backend.cpp MakeMatFromShape 重写）：
  1. 返回**自有 Mat**（数据拷入 ncnn 分配缓冲，逐 channel memcpy），摆脱外部 stride/cstep 耦合；
  2. **rank-4 且 N==1 折叠为 3D**：`[1,C,H,W]` → `Mat(w=W,h=H,c=C)`（batch=1 逻辑等价，
     [1,48,1,1]→Mat(w=1,h=1,c=48) 在 add 中按 w/h=1 广播）；N>1 保留旧 4D 映射+LOGW。
- 验证：python ncnn CPU/VK FP32/FP16/BF16 全过、max diff<4e-4；cl.exe 手工全量编译+链接（绕过
  被拦截的 MSBuild）→ 9 个后端全部出结果：NCNN_VK 48.4ms/1e-8、VK_BF16 53.4ms/3.5e-4、
  VK_FP16 28.2ms/4.2e-5。ONNX_DML_NPU "No devices detected" 是硬件无 NPU 的预期跳过。
- 新工具：tools/probe_vk_crash|steps|walk|fix|verify.py（复现/定位/验证）。
- 经验：**ncnn Vulkan 4D blob 进 BinaryOp 会硬崩**；Vulkan 崩溃先用 python 绑定走中间 blob 缩小到具体算子。
- 构建备注：本机 MSBuild（amd64/x86）Access violation + Git Bash 拦截 LOLBin，本次用
  cl.exe（VS18 MSVC 14.51.36231 Hostx86）手工编译 18 个 cpp + 链接 ncnn.lib 成功产出 exe
  （build/manual_cl/，含 ncnn.dll/onnxruntime.dll 拷贝）。正式构建仍走 VS IDE。
- 后续：probe 脚本已迁至 tools/utils/；safe_extract() 的 minidump 改为 MiniDumpWithFullMemory
  （崩溃时写完整堆栈，便于现场分析），已重编译验证通过。
- 后续：backend_registry.cpp desktop 分支（64/32 位）ONNX_DML_GPU 注册处加注释留档，
  说明 ONNX_DML_GPU_FP16（原 BackendId 3）为何被移除（DML 无 FP16 开关、自动选精度），

## MNN Vulkan NaN 分析 + 新建 docs/MNN_DEBUG_LOG.md
- 问题：Android 上 MNN_VULKAN / MNN_VULKAN_BF16 输出 NaN，MNN_VULKAN_FP16 正常。
- 根因（MNN 官方支持矩阵）：Vulkan BF16 = C（**不支持**，硬跑致 NaN，OpenCL_BF16 同理）；
  Vulkan FP32(Normal) = A（可用但 known issues，MNN Vulkan 用 fp16 中间纹理，Precision_High
  混合精度路径在 Softmax/exp 溢出致 NaN）；Vulkan FP16 = A（全链路自洽，正常）。
- 建议：Android MNN 用 MNN_CPU（S 级）或 MNN_VULKAN_FP16；避免 VULKAN(FP32)/VULKAN_BF16。
- 新建 docs/MNN_DEBUG_LOG.md（现象/根因/结论/经验），README §8 索引同步为 8 篇。
- 待办（用户可选）：MNN_VULKAN_BF16 初始化提前拦截（参照 NCNN BF16 模式），避免 NaN 入 CSV。
